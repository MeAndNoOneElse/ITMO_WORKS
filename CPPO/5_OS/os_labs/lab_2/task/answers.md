# Часть 1. Вопросы на понимание

## 1. Что такое процесс?

**Процесс — это экземпляр выполняющейся программы вместе со всеми ресурсами, которые ОС ему выделила.**

Программа — это пассивный файл на диске (например, `/bin/ls`). Процесс — активная сущность: у него есть состояние, и он меняется во времени. Один и тот же файл можно запустить много раз, и получится много разных процессов.

Что принадлежит процессу:

- уникальный идентификатор **PID** и идентификатор родителя **PPID**;
- **адресное пространство** (код, данные, куча, стек);
- состояние процессора: счётчик команд, регистры, указатель стека;
- таблица **открытых файловых дескрипторов** (0 — stdin, 1 — stdout, 2 — stderr и остальные);
- **переменные окружения**, текущий каталог (cwd), umask;
- права: UID/GID;
- таблица **обработчиков сигналов** и маска сигналов;
- **лимиты ресурсов** (`rlimit`);
- группа процессов, сессия, управляющий терминал.

**Процесс и поток.** Процесс — единица владения ресурсами (память, дескрипторы). Поток — единица планирования внутри процесса: у каждого потока свой стек и регистры, а адресное пространство и дескрипторы общие. В Linux и процессы, и потоки внутри ядра описываются одной структурой `task_struct`.

## 2. Модель состояний процесса

Классическая модель состоит из пяти состояний:

```text
                 допуск ядром
   ┌───────┐ ───────────────► ┌───────┐   выбор планировщиком   ┌───────────┐
   │ New   │                  │ Ready │ ──────────────────────► │ Running   │
   │создан │                  │готов  │ ◄────────────────────── │выполняется│
   └───────┘                  └───────┘   вытеснение (квант     └───────────┘
                                  ▲       времени истёк)         │        │
                                  │                              │        │ exit()
                  событие         │        ожидание события      │        ▼
                  произошло       │        (I/O, sleep, wait)    │   ┌───────────┐
                                  │                              ▼   │Terminated │
                              ┌───────────┐                          │завершён   │
                              │ Blocked   │ ◄────────────────────────┘ (zombie)  │
                              │ожидает    │                              └───────┘
                              └───────────┘
```

Переходы:

| Переход | Причина |
|---|---|
| New → Ready | процесс создан (`fork`) и допущен к планированию |
| Ready → Running | планировщик выбрал процесс и выдал ему процессор |
| Running → Ready | **вытеснение**: закончился квант времени или появился более приоритетный процесс |
| Running → Blocked | процесс ждёт: чтение с диска/из `pipe`, `sleep`, `waitpid` |
| Blocked → Ready | ожидаемое событие произошло (пришли данные, истёк таймер) |
| Running → Terminated | `exit()` или смерть от сигнала |

**Как это выглядит в Linux** (поле `STAT` в `ps`):

| Код | Состояние |
|---|---|
| `R` | Running или Runnable (выполняется или готов) |
| `S` | Interruptible sleep — спит, будится сигналом |
| `D` | Uninterruptible sleep — обычно ждёт диск, сигналами не прерывается |
| `T` | Stopped (по `SIGSTOP`/`Ctrl-Z`) или трассируется отладчиком |
| `Z` | **Zombie** — завершился, но родитель ещё не вызвал `wait` |

## 3. Структура процесса: что содержит, где находится?

У процесса две «половины»:

**1. Описание процесса в памяти ядра.** В Linux это `struct task_struct` (в теории — PCB, Process Control Block). Она недоступна самому процессу. Содержит:

- PID, PPID, состояние, приоритет и данные планировщика;
- сохранённый контекст: регистры, счётчик команд (когда процесс не на процессоре);
- указатель на описание адресного пространства (`mm_struct` с таблицами страниц и списком областей памяти);
- указатель на таблицу файловых дескрипторов (`files_struct`);
- обработчики сигналов, ожидающие сигналы, маску;
- credentials (UID/GID, capabilities), `rlimit`, cwd, root;
- ссылки на родителя, детей, группу процессов и сессию;
- **стек ядра** — отдельный небольшой стек, который используется, когда процесс выполняет системный вызов или обрабатывает прерывание.

**2. Содержимое адресного пространства** — то, что процесс видит как «свою память» (код, данные, куча, стек). Физически это страницы ОЗУ (а часть — на диске, см. вопрос 7).

Посмотреть процесс снаружи можно через `/proc/<pid>/`: `status`, `maps`, `fd/`, `limits`, `stat`, `environ`.

## 4. Адресное пространство процесса: что это и его типовая структура

**Адресное пространство — это набор виртуальных адресов, которые процесс может использовать.** Адреса виртуальные: у каждого процесса своё пространство, и одно и то же число, например `0x401000`, в двух процессах указывает на разные данные. Это даёт **изоляцию**: процесс не видит чужую память.

Типовая раскладка (Linux, x86-64, адреса растут вверх):

```text
старшие адреса
┌────────────────────────────┐
│ пространство ядра          │  отображено, но недоступно из user mode
├────────────────────────────┤
│ argv, envp, auxv           │  аргументы и окружение процесса
├────────────────────────────┤
│ СТЕК                       │  локальные переменные, адреса возврата
│   ↓ растёт вниз            │  (ограничен RLIMIT_STACK)
│                            │
│ ... свободно ...           │
│                            │
│ mmap-область               │  разделяемые библиотеки (libc.so), mmap-файлы,
│                            │  большие malloc
│   ↑ растёт вверх           │
│ КУЧА (heap)                │  malloc/free (brk), растёт вверх
├────────────────────────────┤
│ .bss                       │  глобальные без инициализации (нули)
│ .data                      │  глобальные с инициализацией
│ .rodata                    │  константы, строковые литералы (только чтение)
│ .text                      │  машинный код программы (чтение + исполнение)
└────────────────────────────┘
младшие адреса
```

Права областей: код — `r-x` (нельзя писать), данные и куча — `rw-` (нельзя исполнять, бит NX), константы — `r--`. Нарушение прав даёт `SIGSEGV`.

Особенности:

- **ASLR** — адреса стека, кучи и библиотек случайно сдвигаются при каждом запуске (защита от эксплойтов).
- Посмотреть реальную раскладку: `cat /proc/self/maps` или `cat /proc/<pid>/maps`.
- Дочерний процесс после `fork` получает копию такого же пространства, а `exec` строит его заново.

## 5. Чем функции типа `main()` отличаются от функций типа `fork()`?

Различаются по тому, **сколько раз функция возвращается** и кто её реализует.

| | Как работает |
|---|---|
| **`main()` и обычные функции** | Вызывается один раз, возвращается один раз, всё выполняется в user mode. `main` вызывает не ОС, а код запуска из libc (`_start` → `__libc_start_main` → `main`), и после `return` вызывается `exit`. |
| **`fork()`** | Это обёртка над **системным вызовом**: выполнение переходит в режим ядра. Вызывается **один раз, а возвращается дважды** — в двух разных процессах: у родителя возвращает PID ребёнка, у ребёнка — `0`, при ошибке — `-1`, и ребёнка не создаётся. |
| **`exec*()`** | Вызывается, но при **успехе не возвращается никогда** (образ процесса заменён, возвращаться некуда). Возврат есть только при ошибке (`-1`). |
| **`_exit()`, `exit()`** | Вызывается, но не возвращается — процесс завершается. |

Именно из-за «двойного возвращения» `fork` пишут так:

```c
pid_t pid = fork();
if (pid < 0)       { /* ошибка */ }
else if (pid == 0) { /* код ребёнка */ }
else               { /* код родителя, pid — PID ребёнка */ }
```

## 6. Кто отвечает за переключение процессов? Как он может остановить одну программу посреди выполнения и возобновить другую?

Отвечает **ядро ОС**: его **планировщик** (scheduler) решает, какому процессу отдать процессор, а **диспетчер** (код переключения контекста) делает само переключение. Опирается ядро на аппаратуру — **таймер**, который шлёт прерывания.

**Как прервать программу посреди выполнения:**

1. Программа выполняется на процессоре в user mode и ничего не знает о других.
2. Аппаратный таймер с постоянным периодом (тик, например 1–4 мс) вызывает **прерывание**. Процессор сам, аппаратно, сохраняет минимум состояния (счётчик команд, флаги, указатель стека) и переходит в обработчик прерывания в ядре.
3. Обработчик учитывает использованное процессом время. Если квант исчерпан или появился более приоритетный процесс, ядро помечает, что нужно перепланирование (`need_resched`).
4. Перед возвратом из прерывания вызывается `schedule()`:
   - **сохраняет контекст** текущего процесса (регистры общего назначения, счётчик команд, указатель стека) в его структуру и на стек ядра;
   - **выбирает** следующий процесс из очереди готовых (в Linux — алгоритм CFS/EEVDF);
   - **загружает контекст** выбранного процесса и переключает **таблицы страниц** (регистр CR3 на x86), то есть подменяет адресное пространство.
5. Возврат из прерывания (`iret`/`sysret`) продолжает выполнение **другого** процесса с той команды, на которой он когда-то остановился.

Для самой программы это невидимо: после возобновления все её регистры и память такие же, как были.

Есть и **добровольное** переключение: если процесс вызвал блокирующий системный вызов (`read` из пустого `pipe`, `waitpid`, `sleep`), ядро само переводит его в Blocked и сразу запускает другой процесс. Схема, где ОС может отнять процессор силой, называется **вытесняющей многозадачностью** (в отличие от кооперативной, где программа должна сама отдать управление).

Переключение не бесплатно: сбрасываются кэши и TLB, поэтому слишком частое переключение замедляет систему.

## 7. Откуда берётся адресное пространство процесса и где оно в реальности находится?

**Откуда берётся.** Его создаёт ядро:

- при **`fork`**: ядро копирует структуры адресного пространства родителя, но физические страницы **не копирует сразу**, а помечает общими «только для чтения». Реальная копия страницы делается при первой записи в неё (**copy-on-write**). Поэтому `fork` быстрый;
- при **`exec`**: ядро отбрасывает старое пространство и строит новое по ELF-файлу программы: отображает (`mmap`) сегменты кода и данных из файла, создаёт стек, кладёт на него `argv`/`envp`, подключает динамический загрузчик и библиотеки;
- во время работы: `brk`/`mmap`/`malloc` расширяют его.

**Где находится в реальности.** Процесс оперирует **виртуальными адресами**. Аппаратный блок **MMU** переводит их в физические по **таблицам страниц**, которые лежат в памяти ядра и принадлежат каждому процессу отдельно. В итоге:

- реально данные лежат в страницах **физической ОЗУ** (обычно по 4 КиБ), причём разные процессы с одним виртуальным адресом попадают в разные физические;
- некоторые страницы **ещё не загружены**: код программы подгружается с диска лениво, по мере обращения (**demand paging**; при обращении возникает page fault, ядро подгружает страницу и продолжает выполнение);
- часть страниц может быть выгружена на диск (**swap**);
- одни и те же физические страницы могут быть общими для нескольких процессов (код `libc.so`, COW-страницы после `fork`).

## 8. User Space vs Kernel Space: в чём разница и зачем? Где работает наша программа? Всегда?

**Kernel space** — память и код ядра: полный доступ к железу, ко всей физической памяти, ко всем процессам. Выполняется в привилегированном режиме процессора (ring 0).

**User space** — память и код обычных программ: доступ только к своему адресному пространству, прямой работы с устройствами нет. Выполняется в непривилегированном режиме (ring 3).

**Зачем разделение:**

- **изоляция**: ошибка (или злой умысел) одной программы не уничтожает другие и не роняет систему, а программа не читает чужую память;
- **безопасность**: права проверяет только ядро, программа не может обойти проверки;
- **справедливое распределение ресурсов**: процессор и память делит ядро, программа не может забрать всё себе;
- **стабильность**: при падении программы ядро просто завершает процесс (`SIGSEGV`), а система работает.

**Где работает наша программа.** Основной код (`main`, парсер, ваша логика) — **в user mode**. Но не всегда: когда программа вызывает системный вызов (`fork`, `read`, `waitpid`, `setrlimit`…), процессор переключается в режим ядра, и дальше **код ядра выполняется от имени этого процесса**. Когда вызов закончился, происходит возврат в user mode. В режим ядра исполнение также попадает при прерываниях (таймер) и исключениях (page fault, деление на ноль).

Например, сам `printf` — это код библиотеки в user mode, а вот `write(1, ...)`, который он вызывает внутри, — уже переход в ядро.

## 9. За счёт чего удаётся сделать разделение User / Kernel Mode?

За счёт **аппаратной поддержки процессора**, на которую опирается ядро:

1. **Режимы привилегий** (кольца защиты, на x86 — ring 0 и ring 3; на ARM — EL1 и EL0). Режим хранится в регистрах процессора, и менять его произвольно из user mode нельзя.
2. **Привилегированные инструкции** (работа с таблицами страниц, отключение прерываний, ввод-вывод в порты). В user mode они вызывают исключение, и ядро завершает программу.
3. **MMU и биты в таблицах страниц**: каждая страница имеет флаги «доступна из user mode», «чтение/запись», «запрет исполнения» (NX). Память ядра помечена как «только для supervisor»: обращение из user mode — исключение.
4. **Единственная контролируемая точка входа в ядро** — инструкция системного вызова (`syscall` / `int 0x80` / `sysenter`). Она переходит строго на адрес, заданный ядром заранее, и программа не может «прыгнуть» в произвольное место ядра. Номер вызова и аргументы ядро валидирует.
5. **Прерывания и исключения**. Таймер гарантирует, что управление вернётся ядру, даже если программа зациклилась.
6. Отдельный **стек ядра** для каждого процесса: ядро не доверяет пользовательскому стеку.
7. Программная часть: ядро проверяет все указатели из user space (`copy_from_user`, `copy_to_user`).

## 10. Как с помощью `/proc` увидеть все дочерние процессы?

**Способ 1. Файл `children`** (если ядро собрано с `CONFIG_PROC_CHILDREN`, в большинстве дистрибутивов это так):

```sh
cat /proc/<pid>/task/<pid>/children
# для текущего shell:
cat /proc/$$/task/$$/children
```

Выведет PID'ы **прямых** детей через пробел.

**Способ 2. По полю `PPid`** в `/proc/<pid>/status`. Работает везде:

```sh
grep -l '^PPid:[[:space:]]*<pid>$' /proc/[0-9]*/status 2>/dev/null
# так как путь содержит PID, можно красиво вывести PID'ы:
for f in /proc/[0-9]*/status; do
  awk -v p=<pid> '$1=="PPid:" && $2==p {split(FILENAME,a,"/"); print a[3]}' "$f" 2>/dev/null
done
```

(`2>/dev/null` нужен потому, что процесс может завершиться между перечислением и чтением.)

**Способ 3. `/proc/<pid>/stat`**: четвёртое поле — PPID. Но имя программы во втором поле в скобках может содержать пробелы, поэтому парсить нужно после последней `)`.

**Дерево всех потомков**: `pstree -p <pid>` или `ps --ppid <pid>`; чтобы получить не только прямых детей, нужно рекурсивно повторять способы 1–2.

Через `/proc` также видно: `/proc/<child>/stat` и состояние (`Z` — зомби), `/proc/<child>/fd` и т. д.

## 11. Что такое `rlimit` и что с его помощью можно делать?

**`rlimit` (resource limit)** — механизм ядра, который ограничивает, сколько ресурсов может потребить процесс. У каждого ресурса два значения:

- **soft limit** — реально действующее значение; процесс может менять его сам, в пределах hard;
- **hard limit** — потолок для soft. Обычный пользователь может его только **понижать** (и необратимо); поднять может только привилегированный процесс.

Функции: `getrlimit()`/`setrlimit()` (POSIX), `prlimit()` (Linux, можно менять чужой процесс). В shell: `ulimit` (встроенная команда, использует те же вызовы), `prlimit` (утилита).

Основные лимиты и **что происходит при превышении**:

| Лимит | Что ограничивает | Реакция при превышении |
|---|---|---|
| `RLIMIT_NPROC` | число процессов/потоков **пользователя** | `fork` возвращает `-1`, `errno = EAGAIN` |
| `RLIMIT_NOFILE` | число открытых файловых дескрипторов | `open`/`pipe`/`socket` → `EMFILE` |
| `RLIMIT_FSIZE` | максимальный размер создаваемого файла | процесс получает `SIGXFSZ` (по умолчанию завершается), а при игнорировании `write` возвращает `EFBIG` |
| `RLIMIT_STACK` | максимальный размер стека | `SIGSEGV` |
| `RLIMIT_AS` | размер виртуального адресного пространства | `mmap`/`brk` → `ENOMEM`, `malloc` возвращает `NULL` |
| `RLIMIT_CPU` | процессорное время | `SIGXCPU`, затем `SIGKILL` |
| `RLIMIT_CORE` | размер core-файла | ограничивается или отключается дамп |

**Для чего применяется:**

- защита от «убегающих» программ (бесконечная запись в файл, утечка памяти, fork-бомба);
- простая **песочница** при запуске чужого кода (проверяющие системы, шелл);
- тестирование: проверить, как программа ведёт себя при отказе ресурсов.

**Важные свойства:**

- наследуются при `fork` и **сохраняются при `exec`**, поэтому лимит можно поставить в ребёнке между `fork` и `exec`, не затрагивая родителя (это сделано в нашем шелле);
- действуют на каждый процесс отдельно (кроме `RLIMIT_NPROC`, который считается по реальному UID пользователя);
- проверить текущие значения: `cat /proc/<pid>/limits`.

## 12. Зачем делать `wait()`? И что будет, если не использовать его?

`wait`/`waitpid` нужны для трёх вещей:

1. **Получить результат**: как завершился ребёнок (код возврата или сигнал) — через макросы `WIFEXITED`, `WEXITSTATUS`, `WIFSIGNALED`, `WTERMSIG`. Без этого shell не знал бы статус команды и не смог бы реализовать `||`, `;` и т. д.
2. **Синхронизация**: дождаться завершения. Без `wait` shell напечатал бы следующее приглашение, пока команда ещё выводит данные.
3. **Освободить ресурсы**: пока родитель не сделал `wait`, завершившийся ребёнок остаётся **зомби** (запись в таблице процессов).

**Если не вызывать `wait`:**

- родитель не узнаёт статус детей;
- завершившиеся дети накапливаются как **зомби**: память они уже отдали, но заняты PID и слоты таблицы процессов. При большом числе зомби `fork` начнёт возвращать `-1` с `EAGAIN`;
- если родитель сам завершится, зомби и живых детей усыновит `init` (PID 1) или процесс-subreaper, который сделает `wait`, и зомби исчезнут;
- для долго живущего родителя, как наш shell, это настоящая утечка. Поэтому для фоновых задач нужен регулярный `waitpid(-1, &st, WNOHANG)`.

## 13. Что делает `exec()`? Что содержится в скомпилированной программе?

**`exec` заменяет образ текущего процесса новой программой.** Новый процесс не создаётся: PID остаётся прежним, а код, данные, куча и стек заменяются.

**Что сохраняется после `exec`:** PID и PPID, открытые файловые дескрипторы (кроме помеченных `O_CLOEXEC`), окружение (то, что передали), cwd, UID/GID, `rlimit`, группа процессов и сессия, маска сигналов, **игнорируемые** сигналы (поэтому в нашем шелле ребёнок возвращает `SIGINT` в `SIG_DFL`).

**Что сбрасывается:** адресное пространство целиком, обработчики сигналов (кроме игнорируемых — они возвращаются к `SIG_DFL`), отображения памяти.

**Что делает ядро при `exec`:** открывает файл, проверяет формат (ELF или `#!` скрипт), создаёт новое адресное пространство, отображает в него сегменты, готовит стек с `argv`/`envp`, передаёт управление на точку входа.

**Что содержится в скомпилированной программе** (на Linux — файл формата **ELF**):

- **ELF-заголовок**: тип файла, архитектура, **точка входа** (адрес `_start`);
- **таблица сегментов** (program headers): какие части файла и по каким адресам отображать в память, с какими правами (`PT_LOAD`: код `r-x`, данные `rw-`);
- **секции**: `.text` (машинный код), `.rodata` (константы, строки), `.data` (инициализированные глобальные), `.bss` (неинициализированные глобальные; в файле хранится только размер), `.plt`/`.got` (связь с динамическими библиотеками);
- запись **`PT_INTERP`** — путь к динамическому загрузчику (`ld-linux.so`), который подгрузит `libc.so` и другие зависимости (`DT_NEEDED`);
- таблицы символов и отладочная информация (при `-g`).

**Последовательность запуска:** `exec` → ядро отображает ELF → динамический загрузчик подключает библиотеки → `_start` → `__libc_start_main` → `main(argc, argv, envp)`.

**Семейство функций:** реальный системный вызов один — `execve`. Остальные — обёртки; буквы в имени показывают вариант передачи аргументов:

| Буква | Значение |
|---|---|
| `l` | аргументы списком (`execl("ls", "ls", "-l", NULL)`) |
| `v` | аргументы массивом `argv[]` (`execv`) — как в нашем шелле |
| `p` | искать программу по `PATH` (`execvp`) |
| `e` | явно передать окружение (`execve`, `execle`) |

## 14. Можно ли создать процесс без использования функции типа `fork()`/`clone()`?

**На уровне ядра Linux — нет**: любой новый процесс создаётся через системный вызов `clone`/`clone3` (то есть через общую функцию ядра `kernel_clone`). `fork()` — это `clone` с набором флагов, `vfork()` — `clone(CLONE_VM | CLONE_VFORK)`. Единственные исключения — самый первый процесс и потоки ядра, которые создаёт само ядро при загрузке (`init`, PID 1).

**На уровне программы/библиотеки — да**, можно не вызывать `fork` самому:

- **`posix_spawn()` / `posix_spawnp()`** — стандартная POSIX-функция «создать и сразу запустить» (внутри glibc использует `clone`);
- **`system()`** и **`popen()`** — запускают `/bin/sh -c ...` (внутри тоже `fork`/`clone`); **в нашей работе их использовать нельзя**;
- в других ОС (**Windows**) вообще нет `fork`: используется `CreateProcess` (вопрос 16).

## 15. Почему после создания процесса одна ветвь вызывает `exec`, а другая — `wait`?

После `fork` существуют **две одинаковые копии** одной программы. Работа у них разная:

- **Ребёнок** должен запустить *другую* программу (то, что ввёл пользователь). Для этого он вызывает **`exec`**, который заменяет его образ новой программой.
- **Родитель** (shell) должен остаться shell'ом: дождаться окончания команды и узнать результат. Для этого он вызывает **`wait`**.

```text
          fork()
            │
   ┌────────┴────────┐
   ▼                 ▼
 РЕБЁНОК           РОДИТЕЛЬ
 (pid == 0)        (pid > 0)
   │                 │
 подготовка:         │
 dup2, setrlimit,    │
 setpgid ...         │
   │                 │
 exec(prog)          waitpid(pid) ← ждёт
   │                 │
 [выполняется        │
  prog]              │
   │                 │
 exit ──────────────► статус получен, продолжаем
```

**Почему именно два шага (`fork` + `exec`), а не один «запусти программу»:** между `fork` и `exec` ребёнок, ещё выполняя код shell'а, может **настроить своё окружение**, не затрагивая родителя:

- `dup2` — перенаправить stdin/stdout (так реализуются `pipe` и `>`);
- `setrlimit` — ограничить ресурсы (наш `FSIZE`);
- `setpgid`, сброс сигналов, закрытие лишних дескрипторов.

Если бы `exec` вызывал родитель, **shell перестал бы существовать** — его образ заменился бы программой. Если бы `wait` вызывал ребёнок, ему было бы нечего ждать: у него нет детей. Для фоновых команд (`&`) родитель `wait` не вызывает сразу, а проверяет детей позже, неблокирующе.

## 16. Как в Windows работает создание процесса?

В Windows **нет `fork`**. Новый процесс создаётся **одним вызовом** `CreateProcess`, который сразу и создаёт процесс, и загружает в него программу:

```c
BOOL CreateProcessW(
    LPCWSTR lpApplicationName,     // путь к .exe (или NULL)
    LPWSTR  lpCommandLine,         // командная строка целиком
    LPSECURITY_ATTRIBUTES lpProcessAttributes,
    LPSECURITY_ATTRIBUTES lpThreadAttributes,
    BOOL    bInheritHandles,       // наследовать ли дескрипторы
    DWORD   dwCreationFlags,       // флаги (CREATE_NEW_CONSOLE, CREATE_SUSPENDED ...)
    LPVOID  lpEnvironment,         // окружение
    LPCWSTR lpCurrentDirectory,
    LPSTARTUPINFOW lpStartupInfo,  // stdin/stdout/stderr, окно и т. д.
    LPPROCESS_INFORMATION lpProcessInformation); // сюда вернутся HANDLE и ID
```

Что происходит: система создаёт объект процесса, строит адресное пространство, загружает `.exe` и DLL, создаёт **главный поток** и возвращает дескрипторы (`HANDLE`) процесса и потока.

Отличия от Unix:

| Unix | Windows |
|---|---|
| `fork` + `exec` (два шага, ребёнок — копия родителя) | `CreateProcess` (один шаг, процесс «с нуля») |
| перенаправление через `dup2` в ребёнке | задаётся родителем заранее в `STARTUPINFO` + `bInheritHandles` |
| иерархия родитель/ребёнок, зомби | нет обязательной иерархии, зомби нет; объект процесса живёт, пока открыт `HANDLE` |
| `waitpid`, код возврата в статусе | `WaitForSingleObject(handle, INFINITE)`, `GetExitCodeProcess`, затем `CloseHandle` |
| `rlimit`, группы процессов | **Job Objects** (лимиты памяти, числа процессов), группы консоли |
| сигналы | нет сигналов в Unix-смысле (есть события консоли, `TerminateProcess`) |

Команда передаётся одной строкой, и разбирает её сама запущенная программа (а не shell, как в Unix). Эмуляция `fork` в Windows возможна лишь косвенно (Cygwin, WSL).

## 17. Какие есть в Unix/POSIX способы создать процесс?

| Способ | Что это | Особенности |
|---|---|---|
| **`fork()`** | POSIX | копия родителя (COW-память); ребёнок делает `exec` или продолжает |
| **`vfork()`** | исторический BSD | ребёнок временно **делит память** с родителем, родитель приостановлен до `exec`/`_exit`; в ребёнке можно вызывать почти ничего; в POSIX помечен устаревшим |
| **`clone()` / `clone3()`** | Linux | гибко задаёт, что делить с родителем (память, дескрипторы, сигналы): на нём построены `fork`, `vfork` и потоки (`pthread_create`) |
| **`posix_spawn()`** | POSIX | «`fork`+`exec` одним вызовом» с настройкой дескрипторов, сигналов и т. д. |
| **`system()`** | libc | запускает `/bin/sh -c cmd` и ждёт |
| **`popen()`** | libc | запускает `sh -c` и связывает с ним `pipe` |
| **`exec*()`** | POSIX | процесс **не создаёт**, а заменяет образ текущего |

В этой работе: вариант — `fork`; `system`, `popen` и `/bin/sh -c` запрещены.

## 18. Отличия Unix и POSIX в контексте выполнения работы

- **Unix** — семейство операционных систем (и зарегистрированная торговая марка, т. е. сертификация по Single UNIX Specification). Примеры: macOS (сертифицирована), AIX, Solaris; Linux и BSD — «unix-подобные».
- **POSIX** (IEEE 1003 / ISO) — **стандарт интерфейсов**: какие функции (`fork`, `exec*`, `waitpid`, `pipe`, `dup2`, `sigaction`, `setrlimit`), как должен вести себя shell и стандартные утилиты. Цель — переносимость программ между Unix-системами. Linux официально не сертифицирован как UNIX, но в основном POSIX-совместим.

**В контексте нашей работы:**

- `fork`, `execvp`, `waitpid`, макросы `WIFEXITED`/`WEXITSTATUS`/`WIFSIGNALED`, `pipe`, `dup2`, `setpgid`, `sigaction`, `getrlimit`/`setrlimit`, `isatty`, `getline` — **POSIX**, поэтому код переносим на macOS и BSD;
- `clone`, `/proc`, `prlimit`, `fork` как обёртка над `clone` — **специфика Linux**;
- `vfork` в POSIX помечен устаревшим, вместо него — `posix_spawn`;
- `_GNU_SOURCE` в `vtsh.c` включает расширения glibc: с ним доступны `getline`, `strsignal` и прочее нужное одним макросом (сами эти функции входят в POSIX.1-2008);
- ограничения тоже частично различаются: например, набор доступных `RLIMIT_*` и особенности `RLIMIT_AS` на macOS отличаются.

## 19. Мы рассмотрели, как работает shell, но где т. н. «эмулятор терминала»?

**Shell — это программа, а не окно.** Он читает строки из stdin и пишет в stdout. Окно с текстом, шрифтом, прокруткой и клавиатурой — это отдельная программа: **эмулятор терминала** (GNOME Terminal, xterm, iTerm, Windows Terminal). Он имитирует старые аппаратные терминалы (VT100): принимает нажатия клавиш и рисует текст.

**Как они связаны — через псевдотерминал (PTY):**

```text
 клавиатура
    │
    ▼
┌──────────────────┐   write    ┌─────────────────────────┐   stdin/out/err   ┌────────┐
│ эмулятор         │ ─────────► │ ПСЕВДОТЕРМИНАЛ в ядре   │ ◄───────────────► │ shell  │
│ терминала (GUI)  │ ◄───────── │ master ⇄ line discipline│   /dev/pts/N      │ (vtsh) │
└──────────────────┘   read     │         ⇄ slave         │                   └────────┘
   рисует окно                  └─────────────────────────┘
```

- эмулятор держит **master**-конец PTY, а shell получает **slave**-конец (`/dev/pts/N`) как свои дескрипторы 0, 1, 2;
- между ними в ядре работает **дисциплина линии** (TTY line discipline): сборка строки по Enter, редактирование (Backspace), эхо символов, превращение `Ctrl-C` в `SIGINT`, `Ctrl-D` в EOF;
- эмулятор запускает shell так: `fork` → в ребёнке `setsid`, привязка терминала, `dup2` на 0/1/2 → `exec(shell)`.

Поэтому `isatty(STDIN_FILENO)` в нашем shell истинно при работе в окне терминала и ложно в тестах, где ввод идёт через `pipe` (так приглашение не мешает тестам). Проверить: команда `tty` или `ls -l /proc/$$/fd`.

## 20. Кто такой Zombie? Когда появляется и кто обязан его «убить»?

**Зомби** — процесс, который уже **завершился**, но чей родитель ещё не вызвал `wait`. Память и ресурсы процесса уже освобождены, остаётся только маленькая запись в таблице процессов: PID, код завершения, статистика. В `ps` помечен `Z` или `<defunct>`.

**Зачем ядро хранит запись:** чтобы родитель мог узнать, как завершился ребёнок. Пока он этого не сделал, информацию удалять нельзя.

**Когда появляется:** в промежутке между `exit` ребёнка и `waitpid` родителя. Для shell'а, который ждёт сразу, он живёт доли миллисекунды. Проблемой становится, если родитель вообще не вызывает `wait` (фоновые процессы).

**Кто убивает:**

- **родитель** — вызовом `wait`/`waitpid` (в нашем shell — `reap_jobs()` через `waitpid(-1, &st, WNOHANG)`);
- если родитель завершился, зомби **усыновляет `init` (PID 1)** или ближайший **subreaper** (`prctl(PR_SET_CHILD_SUBREAPER)`) и сразу делает `wait`;
- родитель может заранее попросить ядро не плодить зомби: `signal(SIGCHLD, SIG_IGN)` или флаг `SA_NOCLDWAIT`.

Командой `kill` зомби **убить нельзя**: он уже мёртв. Можно только заставить родителя вызвать `wait` или убить самого родителя (тогда зомби перейдут к `init`).

**Не путать с сиротой (orphan):** сирота — это *живой* процесс, чей родитель умер.

## 21. Что остаётся общего у только что созданного подпроцесса и родительского процесса?

После `fork` ребёнок — почти точная копия родителя.

**Общее (унаследованное или скопированное):**

- **содержимое памяти** — код, данные, куча, стек (отдельные копии, при записи COW; значения переменных совпадают в момент `fork`);
- **место выполнения** — ребёнок продолжает с команды, следующей за `fork`;
- **открытые файловые дескрипторы**: они указывают на **те же** «открытые файловые описания», поэтому у родителя и ребёнка **общая позиция** чтения/записи файла. Именно так дети получают общие `pipe` и терминал;
- переменные окружения, текущий каталог, корневой каталог, umask;
- UID/GID и права;
- **`rlimit`**;
- таблица обработчиков сигналов и маска блокируемых сигналов;
- группа процессов, сессия, управляющий терминал.

**Различается:** PID и PPID, значение, возвращённое `fork` (PID ребёнка у родителя, `0` у ребёнка), ожидающие сигналы (у ребёнка очищаются), таймеры и счётчики времени (обнуляются), блокировки файлов (`fcntl`) не наследуются; в ребёнке остаётся только поток, вызвавший `fork`.

Эта общая часть и нужна shell'у: ребёнок наследует дескрипторы, окружение и лимиты, а затем настраивает то, что отличается, и делает `exec`.

## 22. Что такое `pipe`?

**`pipe` — однонаправленный канал связи между процессами**, реализованный в ядре в виде кольцевого буфера в памяти (в Linux обычно 64 КиБ). Передаёт непрерывный поток байт (без границ сообщений).

```c
int fd[2];
pipe(fd);   // fd[0] — конец для ЧТЕНИЯ, fd[1] — конец для ЗАПИСИ
```

```text
 процесс A ──write(fd[1])──►[ буфер в ядре ]──read(fd[0])──► процесс B
```

Свойства:

- **блокировки**: `read` из пустого канала ждёт данные; `write` в полный канал ждёт освобождения места;
- **EOF**: `read` возвращает `0`, когда **все** дескрипторы записи закрыты и буфер пуст;
- запись в канал, у которого **нет читателей**, приводит к `SIGPIPE` (или к ошибке `EPIPE`);
- запись размером до `PIPE_BUF` (4096 байт в Linux) **атомарна**;
- анонимный `pipe` связывает **родственные** процессы: дескрипторы нужно получить через `fork`. Для неродственных процессов есть именованные каналы (**FIFO**, `mkfifo`).

В shell `a | b` — это два процесса, у которых stdout первого подключён к stdin второго через `pipe` (и `dup2`, см. вопрос 25).

## 23. Можно ли из `pipe` прочитать 0?

Вопрос допускает две трактовки, и **оба ответа — «да»**:

1. **`read()` вернул `0`** — это **конец файла (EOF)**: все дескрипторы записи закрыты, и данных больше не будет. Это нормальный сигнал «читать больше нечего» (а не «прочитан нулевой байт»). Ошибка — это `-1` и `errno`. (Также `read` вернёт `0`, если запросили `count == 0`.)
2. **Прочитан байт со значением `0`** — `pipe` передаёт произвольные байты, включая `'\0'`. Тогда `read` вернёт `n > 0` (число прочитанных байт), а в буфере будет нулевой байт.

Вывод: нужно различать **возвращаемое значение `read`** (сколько байт прочитано) и **содержимое буфера**. Цикл чтения всегда пишут по возвращаемому значению:

```c
ssize_t n;
while ((n = read(fd, buf, sizeof buf)) > 0) { /* обработать n байт */ }
if (n == 0) { /* EOF */ } else { /* n < 0: ошибка */ }
```

## 24. Почему незакрытый конец `pipe` может навсегда задержать EOF?

Читатель получает EOF только тогда, когда в системе **не осталось ни одного открытого дескриптора записи** этого `pipe` — **в любом процессе**. Пока хоть где-то он открыт, ядро считает, что кто-то ещё может записать данные, и читатель **блокируется в `read` навсегда**.

Типичные причины в shell:

- **родитель не закрыл свой `fd[1]`** после создания детей: `printf hello | wc -c` — `wc` прочитал `hello`, а EOF не придёт, пока родитель держит конец записи, и `wc` зависнет;
- **ребёнок унаследовал лишние концы**: из-за `fork` у каждого ребёнка копии *всех* открытых дескрипторов. Читатель, у которого остался открытым собственный `fd[1]`, ждёт сам себя;
- в конвейере из нескольких звеньев ребёнок 1 унаследовал концы `pipe` между звеньями 2 и 3.

**Правило:** сразу после `fork` и `dup2` каждый процесс закрывает **все** концы `pipe`, которые ему не нужны (и оригиналы после `dup2`); родитель после создания всех детей закрывает все свои концы.

Симметричная ситуация: если закрыты все концы чтения, писатель получит `SIGPIPE`.

## 25. Работа с `pipe`: зачем нужен `dup()`?

Программы **«зашиты»** на стандартные дескрипторы: `wc` читает из `0`, `ls` пишет в `1`. Они не знают про `fd[0]` и `fd[1]`. Нужно сделать так, чтобы дескриптор `0` (или `1`) **стал** концом `pipe`.

- `dup(old)` — создаёт копию `old` под **наименьшим свободным** номером (оба указывают на один и тот же объект).
- **`dup2(old, new)`** — делает `new` копией `old`: если `new` был открыт, он сначала закрывается. Именно так подменяют `0/1/2`.
- (`dup3` — как `dup2`, но с флагом `O_CLOEXEC`.)

```c
// ребёнок, у которого stdout должен идти в pipe:
dup2(fd[1], STDOUT_FILENO);   // теперь дескриптор 1 — это конец записи pipe
close(fd[0]);                 // эти два номера больше не нужны:
close(fd[1]);                 // у ребёнка осталась копия под номером 1
execlp("ls", "ls", (char *)NULL);
```

Подмена **переживает `exec`**: запущенная программа пишет в stdout, как обычно, а данные попадают в `pipe`. То же самое и для перенаправления в файл `cmd > file`: `fd = open(file, ...)`, `dup2(fd, 1)`, `close(fd)`.

## 26. Как `Ctrl-C` приводит к завершению процесса?

Цепочка событий:

1. Вы нажимаете `Ctrl-C`; эмулятор терминала записывает в master-конец PTY байт `0x03`.
2. **Дисциплина линии** ядра (режим с флагом `ISIG`) видит, что это символ `INTR` (посмотреть: `stty -a`, строка `intr = ^C`). Программе этот байт **не передаётся**.
3. Ядро посылает сигнал **`SIGINT`** всем процессам **foreground process group** этого терминала.
4. Для процесса действие по умолчанию на `SIGINT` — **завершение**. Ядро завершает процесс «по сигналу 2», а родитель при `waitpid` видит `WIFSIGNALED` и `WTERMSIG == 2` (в shell обычно код `130 = 128 + 2`).
5. Программа может **перехватить** сигнал (`sigaction`) или **игнорировать** его (`SIG_IGN`).

**Что из этого следует для shell:**

- `SIGINT` получает вся foreground-группа, **включая сам shell**, если он там находится. Поэтому в `vtsh.c` shell выставляет `SIG_IGN` на `SIGINT`: `Ctrl-C` не должен его убивать;
- игнорирование **наследуется через `exec`**, поэтому ребёнок первым делом возвращает `SIG_DFL`: иначе `Ctrl-C` не останавливал бы запущенную программу;
- **фоновые** процессы в `vtsh` вынесены в отдельную группу (`setpgid(0, 0)`), поэтому `Ctrl-C` их не задевает.

## 27. Как создать фоновый процесс, который будет жить после завершения работы shell?

**Проблема.** Просто `cmd &` недостаточно. При закрытии терминала ядро шлёт `SIGHUP` лидеру сессии (shell), тот рассылает `SIGHUP` своим заданиям, и они завершаются. Кроме того, у процесса остаётся привязка к терминалу (`stdin/stdout`).

**Способы:**

1. `nohup cmd &` — процесс игнорирует `SIGHUP`, вывод уходит в `nohup.out`;
2. `setsid cmd &` — процесс запускается в **новой сессии** без управляющего терминала, и `SIGHUP` от терминала до него не доходит;
3. `disown` / `disown -h` (в bash) — shell «забывает» задание и не шлёт ему `SIGHUP`;
4. `tmux`/`screen`, `systemd-run` — запуск под управлением другого сервиса;
5. **Классическая демонизация** (двойной `fork`):

```c
#define _GNU_SOURCE
#include <fcntl.h>
#include <signal.h>
#include <stdlib.h>
#include <sys/stat.h>
#include <unistd.h>

static void daemonize(void) {
    pid_t p = fork();
    if (p < 0) exit(1);
    if (p > 0) _exit(0);          // 1) родитель выходит — shell «закончил» задание
    if (setsid() < 0) exit(1);    // 2) новая сессия: нет терминала, не лидер группы shell
    signal(SIGHUP, SIG_IGN);
    p = fork();
    if (p < 0) exit(1);
    if (p > 0) _exit(0);          // 3) второй fork: процесс не лидер сессии,
                                  //    значит, терминал он уже не получит
    if (chdir("/") < 0) _exit(1); // 4) не держать каталог, который могут размонтировать
    umask(0);
    int fd = open("/dev/null", O_RDWR);
    if (fd >= 0) {                // 5) отвязать стандартные дескрипторы
        dup2(fd, 0); dup2(fd, 1); dup2(fd, 2);
        if (fd > 2) close(fd);
    }
}

int main(void) {
    daemonize();
    sleep(60);                    // «полезная работа» демона
    return 0;
}
```

После выхода родителя осиротевший процесс усыновляет `init`, который его и «дожидается» по завершении (зомби не будет).

**Применительно к нашему `vtsh`:** сейчас при `exit`/EOF мы шлём `SIGTERM` фоновым задачам (политика «не оставлять сирот»). Чтобы задачи пережили shell, нужно: убрать `shutdown_jobs()` (или сделать это настройкой), запускать фоновый процесс через `setsid()` вместо `setpgid()` и игнорировать `SIGHUP` в ребёнке.

## 1. Из каких частей состоит ваш shell?

Четыре логические части (раздел 4 задания), все в файле `vtsh.c`:

| Часть | Что делает | Функции в коде |
|---|---|---|
| **REPL** | приглашение (если `isatty`), чтение строки через `getline`, обработка EOF, вызов parser и executor, сбор фоновых процессов перед приглашением и после строки | `main()` |
| **Parser** | строка → «план выполнения» (`plan_t`: массив команд `cmd_t` + оператор перед каждой). Находит синтаксические ошибки. **Процессов не создаёт.** | `parse()`, `cmd_push()`, `plan_add()`, `plan_free()` |
| **Executor** | запуск команд: `fork` → `exec` в ребёнке, `waitpid` в родителе; применение правил `;` и `\|\|` (ленивое вычисление), перевод `wait`-статуса в код (`128+сигнал`), 127/126, builtin'ы | `execute()`, `run_command()`, `run_external()`, `child_exec()`, `decode_status()`, `builtin_*()` |
| **Process manager** | таблица фоновых задач (id, PID, текст команды), неблокирующий сбор завершившихся (`WNOHANG`), завершение задач при выходе | `add_job()`, `reap_jobs()`, `shutdown_jobs()` |

Внутренние сущности: **простая команда** (`cmd_t`: `argv`, завершённый `NULL`) и **план** (`plan_t`: команды, операторы, флаг фона). Расширения варианта: `&` (фон), `||` и `;`, лимит `FSIZE` (встроенная команда `fsize`).

Принципы: parser не создаёт процессы, обработчиков сигналов с логикой нет (сбор детей — в основном цикле), владение памятью понятно (строки принадлежит `plan_t.buf`, массивы `argv` — плану).

## 3. Считать строку и найти позицию символа `$` (или `-1`)

```c
#include <stdio.h>
#include <string.h>
```

## 4. Программа, которая создаёт подпроцесс

```c
#include <stdio.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    pid_t pid = fork();
    if (pid < 0) {                                   // ошибка: ребёнка нет
        perror("fork");
        return 1;
    }
    if (pid == 0) {                                  // ---- РЕБЁНОК ----
        execlp("echo", "echo", "hello from child", (char *)NULL);
        perror("execlp");                            // сюда попадаем ТОЛЬКО при ошибке exec
        _exit(127);                                  // _exit, не exit (см. вопрос 5)
    }
    int st;                                          // ---- РОДИТЕЛЬ ----
    if (waitpid(pid, &st, 0) < 0) {
        perror("waitpid");
        return 1;
    }
    if (WIFEXITED(st))
        printf("child exited with code %d\n", WEXITSTATUS(st));
    else if (WIFSIGNALED(st))
        printf("child killed by signal %d\n", WTERMSIG(st));
    return 0;
}
```

## 5. Что возвращает `exec()` и что с этим делать?

- **При успехе — ничего не возвращает**: образ процесса заменён, возвращаться некуда. Следующая строка кода не выполнится.
- **При ошибке возвращает `-1`** и выставляет `errno`: `ENOENT` (программа не найдена), `EACCES` (нет права на исполнение), `ENOEXEC` (неверный формат файла), `E2BIG` (слишком длинные аргументы/окружение) и т. д.

**Что делать при возврате (то есть при ошибке):**

1. Сообщить причину: `perror`/`strerror(errno)`.
2. **Немедленно завершить ребёнка** через **`_exit`** (не `return` и не `exit`): иначе ребёнок продолжит выполнять код shell'а, и в системе окажется **два shell'а**, каждый читает ввод.
3. Использовать принятые коды: **127** — программа не найдена (`ENOENT`), **126** — найдена, но запустить нельзя (остальные ошибки).

Почему `_exit`, а не `exit`: `exit` сбрасывает буферы `stdio` и вызывает обработчики `atexit`, дублированные в ребёнке с родителя. Это может вывести лишнее (например, дважды напечатать данные из буфера). `_exit` завершает процесс сразу. Родитель получит этот код из `waitpid`.

В `vtsh.c`:

```c
execvp(c->argv[0], c->argv);
int e = errno;
fprintf(stderr, "vtsh: %s: %s\n", c->argv[0], strerror(e));
_exit(e == ENOENT ? 127 : 126);
```

## 6. Какой порядок правильный: `exec` + `fork` или `exec` + `wait`?

Ни тот ни другой. **Правильный порядок: `fork`, а затем — в ребёнке `exec`, в родителе `wait`.**

```text
fork ──► ребёнок: [подготовка] → exec
     └─► родитель: wait
```

Почему неверны предложенные варианты:

- **`exec` + `fork`**: после успешного `exec` образ процесса заменён, и `fork` не выполнится (он «стёрт»). А если `exec` не удался, то `fork` после него бессмысленен: запускать уже нечего.
- **`exec` + `wait`**: после успешного `exec` вызова `wait` в программе уже нет. К тому же `wait` нужен тому, кто **создал** процесс (родителю), а не тому, кто делает `exec`. Если `exec` сделал сам shell (без `fork`), то shell **исчезнет**, превратившись в запущенную программу.

Каждый вызов относится к своей ветви: `exec` — к ребёнку (подмена образа), `wait` — к родителю (ожидание результата). См. также вопрос 15 части 1.

## 7. Как создаётся `pipe`?

Системным вызовом `pipe(int fd[2])`: ядро создаёт буфер и возвращает **два дескриптора** — `fd[0]` (чтение) и `fd[1]` (запись). Вызов делают **до `fork`**, чтобы дети унаследовали оба конца.

Пример для `ls | wc -l`:

```c
#include <stdio.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    int fd[2];
    if (pipe(fd) < 0) { perror("pipe"); return 1; }

    pid_t a = fork();
    if (a == 0) {                                  // звено 1: ls
        dup2(fd[1], STDOUT_FILENO);                // stdout → в pipe
        close(fd[0]); close(fd[1]);                // оба номера больше не нужны
        execlp("ls", "ls", (char *)NULL);
        perror("ls"); _exit(127);
    }

    pid_t b = fork();
    if (b == 0) {                                  // звено 2: wc -l
        dup2(fd[0], STDIN_FILENO);                 // stdin ← из pipe
        close(fd[0]); close(fd[1]);
        execlp("wc", "wc", "-l", (char *)NULL);
        perror("wc"); _exit(127);
    }

    close(fd[0]); close(fd[1]);                    // РОДИТЕЛЬ: закрыть оба, иначе wc не увидит EOF
    waitpid(a, NULL, 0);
    waitpid(b, NULL, 0);                           // статус конвейера — статус последнего звена
    return 0;
}
```

(Для краткости не проверены ошибки `fork`.) Для конвейера из `n` звеньев нужно `n-1` каналов: звено `i` читает из канала `i-1` и пишет в канал `i`, и каждый процесс закрывает все остальные концы. Родитель дожидается **всех** звеньев.

## 8. Зачем закрывается `pipe`?

1. **Чтобы читатель получил EOF**: EOF наступает, когда закрыты *все* дескрипторы записи (вопрос 24 части 1). Незакрытый конец вызывает зависание.
2. **Чтобы писатель узнал об отсутствии читателей**: когда закрыты все концы чтения, `write` даёт `SIGPIPE`/`EPIPE`, и писатель не будет записывать данные впустую.
3. **Чтобы не исчерпать лимит дескрипторов**: каждый открытый конец — это дескриптор, а их число ограничено `RLIMIT_NOFILE`. Утечки в длительно работающем shell приводят к `EMFILE`.
4. **Чтобы освободить ресурсы ядра**: буфер `pipe` удаляется, когда закрыты оба конца.
5. **Для чистоты окружения запускаемых программ**: лишние дескрипторы не должны утекать в дочерние программы.

Закрывать нужно: (а) ненужный конец в каждом процессе сразу после `fork`; (б) оригинал после `dup2`; (в) все концы в родителе после запуска всех детей.

## 9. Как задаётся ограничение на ресурсы процесса?

Через **`setrlimit()`** (читать текущие значения — `getrlimit()`). Для нашего варианта это `RLIMIT_FSIZE`. Ограничение ставится **в ребёнке, после `fork` и до `exec`**: тогда оно действует только на запущенную программу (наследуется её потомками), а у самого shell лимиты не меняются.

```c
#include <stdio.h>
#include <sys/resource.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    pid_t pid = fork();
    if (pid == 0) {
        rlim_t limit = 4096;                        // байт; в vtsh задаётся командой «fsize 4096»

        struct rlimit rl;
        if (getrlimit(RLIMIT_FSIZE, &rl) < 0) { perror("getrlimit"); _exit(126); }
        if (rl.rlim_max != RLIM_INFINITY && limit > rl.rlim_max) {
            fprintf(stderr, "limit above hard limit\n"); _exit(126);
        }
        rl.rlim_cur = limit;                        // soft — то, что действует
        rl.rlim_max = limit;                        // hard — чтобы программа не подняла soft обратно
        if (setrlimit(RLIMIT_FSIZE, &rl) < 0) {     // не удалось — НЕ запускаем без лимита
            perror("setrlimit"); _exit(126);
        }
        execlp("dd", "dd", "if=/dev/zero", "of=/tmp/out.bin", "bs=1024", "count=100", (char *)NULL);
        perror("exec"); _exit(127);
    }
    int st;
    waitpid(pid, &st, 0);
    if (WIFSIGNALED(st)) printf("killed by signal %d (SIGXFSZ=%d)\n", WTERMSIG(st), SIGXFSZ);
    return 0;
}
```

Нюансы:

- нужно учитывать исходные значения из `getrlimit`: обычный пользователь **не может поднять hard limit**, только понизить;
- ошибки `setrlimit` проверяют обязательно, и программу без заданного ограничения не запускают;
- при превышении `RLIMIT_FSIZE` процесс получает **`SIGXFSZ`** (по умолчанию завершается, код `128+25`), а если сигнал игнорируется — `write` возвращает `-1/EFBIG`;
- проверить действующие лимиты: `cat /proc/<pid>/limits`, `prlimit --pid <pid>`;
- в `vtsh` — встроенная команда `fsize <байты>` (и `fsize off`), которую `child_exec` применяет перед `exec`;
- для `vfork` так нельзя (в ребёнке после `vfork` нельзя вызывать `setrlimit` до `exec`): понадобилась бы программа-обёртка.


Что делает `gcc`: препроцессор (`#include`, `#define`) → компилятор (C → ассемблер) → ассемблер (→ объектный файл `.o`) → компоновщик `ld` (связывает объектные файлы и динамически подключает `libc`) → ELF-файл. Для поиска ошибок памяти полезно добавить санитайзеры: `-g -fsanitize=address,undefined`. Тесты запускаются командой `python3 -m unittest discover -s test`.

## 11. Программа, которая считает длину вводимой строки

```c
#include <stdio.h>

int main(void) {
    int c;
    size_t len = 0;
    while ((c = getchar()) != EOF && c != '\n')    // читаем до конца строки или EOF
        len++;
    printf("%zu\n", len);
    return 0;
}
```

Вариант с `fgets` (ограничена размером буфера, строки длиннее обрежутся):

```c
#include <stdio.h>
#include <string.h>

int main(void) {
    char buf[1024];
    if (!fgets(buf, sizeof buf, stdin)) { puts("0"); return 0; }
    buf[strcspn(buf, "\n")] = '\0';                // не считать '\n'
    printf("%zu\n", strlen(buf));
    return 0;
}
```

## 13. Сколько файловых дескрипторов в вашем процессе?

**Обычно 3**: `0` (stdin), `1` (stdout), `2` (stderr). Они унаследованы от родителя (терминал или `pipe` теста). У нашего shell'а других постоянно открытых дескрипторов нет: `getline` их не открывает.

Нюансы:

- номер нового дескриптора — **наименьший свободный**, поэтому первый `open` обычно вернёт `3`;
- на время выполнения конвейера добавляется по `2` дескриптора на каждый `pipe` (и закрывается после `dup2`);
- у фоновой команды в `vtsh` дескриптор `0` перенаправлен на `/dev/null`;
- если shell запущен из IDE или другого процесса, лишние дескрипторы могут быть унаследованы, и их будет больше;
- **максимум** определяется `RLIMIT_NOFILE` (часто soft = 1024), и при превышении `open`/`pipe` вернут `EMFILE`.

Проверка:

```sh
ls -l /proc/self/fd      # дескрипторы процесса ls (+ один, которым ls читает этот каталог)
ls -l /proc/<pid>/fd     # дескрипторы любого процесса
ulimit -n                # soft-лимит NOFILE текущего shell
```

# Возможные утечки памяти и проблемы, и как мы их решили

## Утечки памяти

| Проблема | Где могла возникнуть | Как решено |
|----------|---------------------|------------|
| **Утекает `buf` в `plan_t`** | Один общий буфер для всех строк плана выделялся через `xrealloc`, но при ошибке парсинга мог не освобождаться. | В `parse()` при `rc != 0` вызывается `plan_free(p)`, который освобождает `p->buf`. В `main()` после `execute()` всегда вызывается `plan_free(&plan)`. |
| **Утекает `argv` команды** | Массив `argv` расширяется через `xrealloc` при каждом `cmd_push`. При ошибке парсинга после сбора части команды память могла остаться. | В `parse()` метке `out` вызывается `free(cur.argv)` для текущей недобавленной команды, а `plan_free(p)` освобождает `argv` всех уже добавленных команд. |
| **Утекает `toks`** | Временный массив указателей на токены выделялся в `parse()` и мог не освобождаться при ошибке. | В метке `out` вызывается `free(toks)` в любом случае (и при успехе, и при ошибке). |
| **Утекает `text` в `g_jobs`** | Текст команды фоновой задачи копировался через `xstrdup` и мог остаться в таблице. | В `reap_jobs()` и `shutdown_jobs()` вызывается `free(g_jobs[i].text)` перед очисткой слота. |

## Возможные блокировки (зависания)

| Проблема | Где могла возникнуть | Как решено |
|----------|---------------------|------------|
| **Зависание в `waitpid` при выходе** | `shutdown_jobs()` посылает `SIGTERM` фоновым задачам и ждёт их через `waitpid`. Если процесс игнорирует `SIGTERM`, оболочка зависнет навсегда. | В текущей реализации это допустимое поведение — оболочка ждёт завершения фоновых задач перед выходом. Если нужно預отвратить, можно посылать `SIGKILL` после таймаута. |
| **Зависание при чтении `pipe` в конвейере** | Если родитель не закрывает свои концы pipe'ов после создания всех детей конвейера, последнее звено никогда не получит EOF и зависнет в `read`. | В `run_pipeline()` родитель закрывает все свои концы pipe'ов в цикле после создания всех fork'ов. |
| **Запуск команды в фоне с конвейером** | Конвейер с `&` не добавлялся в таблицу фоновых задач, его PID терялся, и processus devenait zombie. | Фоновый конвейер не добавляется в таблицу (по варианту требуется только фон одной простой команды). Это известное ограничение. |

# Часть 3. Ответы на вопросы по лабораторной работе

## 1. Зачем операционной системе нужна командная оболочка

**Командная оболочка (shell)** — это пользовательский интерфейс к операционной системе. Она нужна для того, чтобы пользователь мог:

- **Запускать программы** с заданными аргументами командной строки.
- **Управлять процессами**: запускать их в фоне (`&`), дожидаться завершения, прерывать (`Ctrl+C`).
- **Соединять программы** в конвейеры (`|`), чтобы вывод одной программы становился входом другой.
- **Выполнять команды последовательно** (`;`) или условно (`||`, `&&`).
- **Перенаправлять ввод/вывод** в файлы (`>`, `<`, `2>`).
- **Автоматизировать рутину** через скрипты (последовательности команд в файле).

Без оболочки пользователю пришлось бы самостоятельно писать программы на C, вызывать `fork`/`exec`/`waitpid` для каждой запускаемой утилиты. Оболочка берет на себя разбор командной строки, создание процессов и сбор их статусов.

## 2. Как создаются и завершаются процессы

### Создание процессов

В Unix-системах новый процесс создаётся через системный вызов **`fork()`**:

- `fork()` клонирует текущий процесс: после вызова существует два одинаковых процесса — родитель и ребёнок.
- У родителя `fork()` возвращает PID ребёнка (> 0).
- У ребёнка `fork()` возвращает `0`.
- При ошибке возвращается `-1`.

После `fork()` ребёнок обычно вызывает **`execvp()`** (или другой вариант из семейства `exec`), который заменяет его образ на новую программу. PID остаётся тем же, но код, данные и стек подменяются.

Альтернативы: `vfork()`, `clone()` / `clone3()` (Linux-специфичные), `posix_spawn()` (POSIX, внутри использует `clone`).

### Завершение процессов

Процесс завершается вызовом **`exit(code)`** или **`_exit(code)`**:

- `exit()` — библиотечная функция, сбрасывает буферы stdio, вызывает обработчики `atexit`, затем делает системный вызов `exit_group`.
- `_exit()` — системный вызов, завершает процесс immediatamente, без очистки буферов.

После завершения процесс становится **«зомби»** — его ресурсы освобождаются, но запись в таблице процессов остаётся, пока родитель не вызовет `waitpid()` для получения статуса.

## 3. Чем отличаются родительский и дочерний процессы

| Характеристика | Родитель | Ребёнок (после fork) |
|----------------|----------|---------------------|
| Возврат `fork()` | PID ребёнка (> 0) | `0` |
| PID | собственный | новый, выданный ядром |
| PPID | собственный родитель | PID родителя |
| Адресное пространство | своё | копия родителя (COW — copy-on-write) |
| Открытые файловые дескрипторы | свои | копии тех же описаний файлов (общая позиция чтения/записи) |
| Переменные окружения | свои | копия родителя |
| Текущий каталог | свой | копия родителя |
| Обработчики сигналов | свои | копия родителя (игнорируемые сигналы сохраняются через exec) |
| rlimit | свои | копия родителя |

После `exec()` в ребёнке адресное пространство полностью заменяется, но PID, PPID, открытые дескрипторы, переменные окружения, cwd, rlimit сохраняются.

## 4. Как передаются аргументы и переменные окружения

### Аргументы командной строки

Аргументы передаются в массив `argv[]`:

```c
int main(int argc, char *argv[], char *envp[])
```

- `argc` — количество аргументов (включая имя программы).
- `argv[0]` — имя программы.
- `argv[1]...argv[argc-1]` — аргументы пользователя.
- `argv[argc]` — всегда `NULL` (терминатор).

Оболочка разбивает введённую пользователем строку на слова (токены), формирует `argv` и передаёт его в `execvp(c->argv[0], c->argv)`.

### Переменные окружения

Переменные окружения передаются через массив `envp[]` (третий аргумент `main`) или через глобальную переменную `environ`:

```c
extern char **environ;
```

Каждый элемент — строка вида `"ИМЯ=ЗНАЧЕНИЕ"`. Окружение наследуется при `fork` и сохраняется при `exec`. Оболочка может изменять своё окружение (команды `export`, `set`), и изменения передаются всем дочерним процессам.

## 5. Как оболочка получает код завершения программы

После того как ребёнок завершился (вызвал `exit` или был убит сигналом), он становится зомби. Родитель (оболочка) должен вызвать **`waitpid()`** для получения статуса:

```c
pid_t pid = waitpid(child_pid, &status, 0);
```

Функция `waitpid` возвращает «сырой» статус, из которого извлекаются коды с помощью макросов:

- `WIFEXITED(status)` — процесс завершился нормально через `exit()`.
  - `WEXITSTATUS(status)` — код возврата (0–255).
- `WIFSIGNALED(status)` — процесс убит сигналом.
  - `WTERMSIG(status)` — номер сигнала.
- Код возврата оболочки при смерти от сигнала — `128 + номер сигнала` (например, `130` для `SIGINT`).

В VTSH функция `decode_status()` реализует эту логику и возвращает внутренний код, который сохраняется в `g_status` и используется встроенной командой `exit`.

## 6. Как реализуются последовательное, условное и фоновое выполнение

### Последовательное выполнение (`;`)

Команды выполняются одна за другой, независимо от статуса предыдущей:

```
cmd1 ; cmd2 ; cmd3
```

В парсере `;` создаёт оператор `OP_SEQ`. В `execute()` каждая команда запускается без проверки статуса предыдущей.

### Условное выполнение (`||`)

Следующая команда запускается только если предыдущая вернула ненулевой статус (ошибку):

```
false || echo "произошла ошибка"
```

В парсере `||` создаёт оператор `OP_OR`. В `execute()` перед запуском команды проверяется `status == 0`: если предыдущая команда успешно завершилась, следующая пропускается (ленивое вычисление).

### Фоновое выполнение (`&`)

Команда запускается в фоне — оболочка не ждёт её завершения и сразу показывает следующее приглашение:

```
sleep 10 &
```

В парсере `&` допускается только в конце строки. В `run_external()` после `fork()` родитель не вызывает `waitpid()`, а добавляет задачу в таблицу `g_jobs` и возвращает управление в REPL. Завершённые фоновые задачи собираются через `reap_jobs()` (`waitpid` с `WNOHANG`).

*(В текущем варианте варианта логические операторы `||` и `;` не поддерживаются — реализованы только `|` и `&`.)*

## 7. Как устроены сигналы, группы процессов и каналы (pipe)

### Сигналы

Сигнал — асинхронное уведомление процессу о событии. Примеры:

- `SIGINT` (2) — `Ctrl+C`, завершение по умолчанию.
- `SIGTERM` (15) — корректное завершение.
- `SIGKILL` (9) — немедленное завершение, не может быть перехвачено.
- `SIGCHLD` — ребёнок завершился или остановился.
- `SIGXFSZ` (25) — превышен лимит размера файла (`RLIMIT_FSZ`).

Процесс может установить обработчик сигнала через `sigaction()`, игнорировать сигнал (`SIG_IGN`) или использовать обработку по умолчанию (`SIG_DFL`). Через `exec()` игнорируемые сигналы сохраняются, остальные сбрасываются в `SIG_DFL`.

### Группы процессов

Группа процессов — набор процессов с одним `PGID`. Используется для управления набором процессов целиком:

- **Foreground group** — процессы, получающие сигналы от терминала (`Ctrl+C` шлёт `SIGINT` всей foreground группе).
- **Background group** — фоновые задачи, не получающие сигналы от терминала.

В VTSH при запуске в фоне (`&`) ребёнок вызывает `setpgid(0, 0)` — создаёт свою группу с `PGID = PID`. Это позволяет `Ctrl+C` не задевать фоновые задачи.

### Каналы (pipe)

`pipe()` создаёт однонаправленный канал связи между двумя процессами:

```c
int fd[2];
pipe(fd);   // fd[0] — чтение, fd[1] — запись
```

Данные, записанные в `fd[1]`, можно прочитать из `fd[0]`. Канал реализован ядром как кольцевой буфер.

Для конвейера `a | b | c`:

1. Создаётся `n-1` каналов для `n` команд.
2. Каждый процесс `i` через `dup2()` подключает stdin к каналу `i-1` и stdout к каналу `i`.
3. Все неиспользуемые концы каналов закрываются в каждом процессе.
4. Родитель закрывает все свои концы каналов после создания детей (иначе последнее звено никогда не получит EOF и зависнет в `read`).

Важное свойство: EOF на чтении наступает только когда закрыты **все** концы записи канала во всех процессах.

## 8. Коды возврата оболочки: подробная теория

### 8.1. Что возвращает `waitpid()`

Когда дочерний процесс завершается, ядро не удаляет его сразу из таблицы процессов — процесс становится **«зомби»**. Родитель должен вызвать `waitpid(pid, &status, 0)`, чтобы получить информацию о завершении.

Функция `waitpid` возвращает PID завершённого ребёнка, а в переменную `status` записывает **«сырой» статус** — целое число, в котором zakodirovano, каким образом processus завершился. Этот статус нельзя читать как обычный код возврата: его нужно декодировать специальными макросами.

### 8.2. Макросы декодирования статуса

| Макрос | Значение | Что возвращает |
|--------|----------|----------------|
| `WIFEXITED(status)` | Процесс завершился нормально через `exit()` | истинно, если нормальное завершение |
| `WEXITSTATUS(status)` | Код возврата, переданный в `exit()` | число от 0 до 255 |
| `WIFSIGNALED(status)` | Процесс был убит сигналом | истинно, если смерть от сигнала |
| `WTERMSIG(status)` | Номер сигнала, убившего процесс | например, 2 для `SIGINT` |

### 8.3. Как оболочка вычисляет свой код возврата

Оболочка переводит «сырой» статус `waitpid` в свой код возврата по следующим правилам:

| Ситуация | Код возврата оболочки | Обозначение |
|----------|----------------------|-------------|
| Программа завершилась через `exit(N)` | `N` (0–255) | `WEXITSTATUS(status)` |
| Программа убита сигналом `S` | `128 + S` | сигнал + смещение |
| Программа не найдена (`ENOENT`) | `127` | соглашение Unix |
| Программа найдена, но не запускается (`EACCES`, `ENOEXEC` и т.п.) | `126` | соглашение Unix |
| Синтаксическая ошибка оболочки | `2` | внутренняя ошибка парсинга |

### 8.4. Почему именно `128 + сигнал`?

Код возврата процесса хранится в одном байте (0–255). Сигналы имеют номера от 1 до 31 (в зависимости от системы). Если бы мы использовали номер сигнала напрямую, он мог бы пересекаться с обычными кодами возврата программ (например, сигнал 1 = `SIGHUP` и код возврата 1 — это разные вещи).

Чтобы избежать пересечения, оболочка прибавляет **128** к номеру сигнала:

| Сигнал | Номер | Код оболочки | Что это значит |
|--------|-------|--------------|----------------|
| `SIGINT` | 2 | `128 + 2 = 130` | прерван `Ctrl+C` |
| `SIGQUIT` | 3 | `128 + 3 = 131` | прерван `Ctrl+\` |
| `SIGKILL` | 9 | `128 + 9 = 137` | убит безвозвратно |
| `SIGSEGV` | 11 | `128 + 11 = 139` | неверный доступ к памяти |
| `SIGTERM` | 15 | `128 + 15 = 143` | корректное завершение |
| `SIGXFSZ` | 25 | `128 + 25 = 153` | превышен лимит размера файла |

### 8.5. Примеры в коде `vtsh.c`

Функция `decode_status(int st)` реализует эту логику:

```c
static int decode_status(int st) {
    if (WIFEXITED(st))
        return WEXITSTATUS(st);           // код 0–255
    if (WIFSIGNALED(st)) {
        int s = WTERMSIG(st);
        fprintf(stderr, "vtsh: terminated by signal %d (%s)\n", s, strsignal(s));
        return 128 + s;                   // 128 + номер сигнала
    }
    return 1;
}
```

А в `run_external()` при ошибке `execvp` возвращаются согласованные коды:

```c
fprintf(stderr, "vtsh: %s: %s\n", cmds[i].argv[0], strerror(errno));
_exit(errno == ENOENT ? 127 : 126);
```

- **127** — программа не найдена (`errno == ENOENT`).
- **126** — программа найдена, но не может быть запущена (нет прав на исполнение, неверный формат файла и т.п.).

### 8.6. Код возврата оболочки и команда `exit`

Оболочка сохраняет код последней выполненной команды в глобальную переменную `g_status`. Когда пользователь вводит `exit` без аргументов, оболочка возвращает `g_status` как свой код выхода:

```c
int builtin_exit(cmd_t *c) {
    int code = g_status;   // код последней команды по умолчанию
    ...
    g_should_exit = 1;
    return code;
}
```

Если пользователь пишет `exit 7`, оболочка завершается с кодом 7, игнорируя `g_status`.
